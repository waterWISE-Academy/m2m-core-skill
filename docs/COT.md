# 🧠 M2M 核心思維鍊與設計哲學 (Chain of Thought & Philosophy)

> **定位聲明**：本文件為 M2M Agentic Protocol 的「憲法」。任何後續的工具迭代、流程修改或架構擴充，皆不可違背本文件所揭示的核心信仰與精神。

---

## 1. 核心信仰 (Core Philosophy)

### 1.1 價值的分離：決策大腦 vs. 實作肌肉
在傳統軟體工程中，人類開發者經常在「思考商業邏輯」與「撰寫底層程式碼」之間來回切換，導致嚴重的認知損耗。
M2M 協議的核心信仰是：**徹底剝離這兩項工作**。
*   **人類的唯一價值**：在於高階的商業定義、承擔風險決策、以及定義不可妥協的邊界 (Constraints)。人類是這間工廠的「老闆/投資人」。
*   **AI 的唯一價值**：在於承擔勞力密集的技術實作、處理繁瑣的語法細節，以及執行無聊的自動化測試。AI 是這間工廠的「工程團隊」。

### 1.2 技術衝突的內部化 (No Tech Approvals)
老闆不應該在會議室裡評理工程師的技術爭執。系統架構的選擇、資料庫的欄位命名、套件的依賴版本，這些純技術問題應由 AI 團隊在背景自行「內部仲裁」。人類核准關卡 (Approval Gates) **僅保留給牽涉商業價值變動**（如成本暴增、範圍無法達成、或專案最終上線交付）的情境。

## 2. 快思慢想架構 (System 1/2 Architecture)

單一 AI Agent 處理複雜專案必定失敗，因為大型語言模型 (LLM) 在長對話中極易產生「幻覺 (Hallucination)」與「注意力偏移」。M2M 透過導入諾貝爾經濟學獎得主康納曼的《快思慢想》模型來解決此問題。

### 2.1 系統一：快思 (Antigravity)
*   **特質**：直覺、發散、高速生成。
*   **任務**：負責快速建構 UI 雛形、產出樣板程式碼 (Boilerplate)、以及根據錯誤日誌進行膝跳反射式的局部修復。它不需要理解全局，只需把眼前的磚塊砌好。

### 2.2 系統二：慢想 (Jules)
*   **特質**：邏輯、收斂、深度審查。
*   **任務**：負責讀取老闆的藍圖、制定技術架構、拆解任務分配給系統一，並在系統一提交程式碼後進行嚴酷的 Code Review。
*   **內部仲裁權**：Jules 永遠擁有最終的技術否決權。當它認為 Antigravity 的程式碼有資安風險或邏輯瑕疵時，可以直接退回重啟，確保程式碼品質。

## 3. 零接觸與絕對隔離 (Zero-Touch & Context Hygiene)

### 3.1 嚴禁本地 AI IDE (Anti-Local-Agent Policy)
為追求開發體驗，現代開發者常依賴 Cursor 或 Cline 等本地 AI IDE。**但在 M2M 框架中，這是被絕對禁止的。**
*   **原因 1 (上下文污染)**：在本地 IDE 進行長時間的對話與除錯，會導致 Agent 的 Context 充滿歷史錯誤與雜訊，最終寫出如義大利麵般混亂的程式碼。
*   **原因 2 (逃避稽核)**：本地修改的程式碼缺乏完整的思考軌跡與 CI 失敗紀錄，將導致系統無法學習與進化。

### 3.2 版本控制系統 (VCS) 作為唯一溝通介面
所有的開發指令、程式碼修改、與除錯對話，必須強制透過 GitHub/GitLab 的 Issue 與 Pull Request 進行。
透過 CI 觸發的每一次自動除錯，Agent 都是在「乾淨的、全新的虛擬環境」中啟動，以上帝視角冷靜地看待錯誤，從源頭斬斷「鬼打牆」的無限迴圈。

## 4. 蜂巢記憶體理論 (Global Hive Memory)

### 4.1 軟體熵增的終結
一般專案會隨著時間推移與人員更迭而腐化（軟體熵增），因為「教訓」通常只存在於開發者的腦海中。

### 4.2 Hub-and-Spoke 與藍圖同步 (Blueprint Sync)
M2M 系統採用 Hub-and-Spoke 架構（中央代工廠與終端 APP）。
核心引擎 (`m2m-core-skill`) 扮演中央大腦。在每一次任務結束前（Merge PR 前），Jules 強制執行「藍圖盤點」，將本次踩過的坑與新制定的規則，寫入該專案的 `docs/LEARNINGS_AND_RULES.md`。
透過這個機制，專案獲得了「長期肌肉記憶」。AI 犯過一次的錯，會永遠固化為全域免疫抗體，讓專案越開發越聰明。
